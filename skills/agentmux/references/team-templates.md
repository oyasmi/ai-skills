# 按需组合角色：七角色开发样例

本文介绍如何让 pipiclaw 这类个人助手通过 agentmux 组合多个角色。这是进阶用法：
日常任务优先选一个合适角色直接委派，只在工作本身需要分工、独立判断或多阶段交付时组建团队。
文中的七角色来自一套实际使用的开发团队配置；可复制样例保留了它的职责、交接和质量准则，
同时压缩了常驻提示词并将账号特定模型改成可替换配置，便于在其他机器上起步。

## agentmux 在团队中的位置

agentmux 管理角色模板和运行实例，不替个人助手做项目管理。上层助手仍然负责：

1. 理解用户意图和当前上下文。
2. 从 `template list --json` 的 `description` 中选角色。
3. 将已知事实、边界和完成定义组织成任务契约。
4. 管理角色之间的交接、反馈回路和并行隔离。
5. 直接检查产物并决定是否向用户交付。

因此，“团队模板”本质上是一组可被上层助手选择和编排的职责契约，不是一个会自动按固定流程运转的工作流引擎。

## 七角色开发团队样例

这套样例将开发工作分成七种不同的判断或产出责任：

| 角色 | 核心责任 | 典型输入 | 典型交付 | 成本定位 |
| --- | --- | --- | --- | --- |
| `planner` | 需求澄清、方案设计、验收定义和任务拆解 | 原始需求、业务背景、仓库现状 | 需求/设计/实施文档、验收标准、角色任务契约 | 高 |
| `builder` | 产品代码实现与单元测试 | 已收敛的任务契约 | 代码、单元测试、实现自查和风险交接 | 中高 |
| `reviewer` | 对方案、实现或文档独立挑错 | 原始需求、验收标准、稳定产物 | 可接受性结论、有证据的编号发现、评审报告 | 中高 |
| `verifier` | 实际运行、冒烟、回归和运行数据分析 | 待验版本、验收标准、环境与数据 | 通过/失败/阻塞矩阵、复现证据、验证脚本与报告 | 中低 |
| `documenter` | 文档、变更记录、提交和最终交付 | 已批准方案、实现、评审与验证证据 | 各类文档、changelog、commit、可追溯交付摘要 | 中 |
| `worker` | 专用角色未覆盖的多步分析与产出 | 问题、数据源、口径、输出形式 | 数据对比、效果分析、转换产物、专项报告 | 中 |
| `scout` | 快速单点事实查询 | 一个事实问题和检索线索 | 直接答案和 `path:line`/命令证据 | 低 |

核心闭环是：

```text
planner ──方案──> reviewer
   │                  │ 问题回流给 planner
   └─任务契约─> builder ──实现──> reviewer
                                      │ 问题回流给 builder
                                      └─通过后─> verifier
                                                    │ 失败回流给 builder
                                                    └─证据─> documenter ──> 最终交付

worker: 在任意阶段承接数据、分析、转换和专项报告
scout:  为任意角色快速补充一个有证据的事实
```

这是责任关系，不是强制顺序。`verifier` 可以在实现前建立基线或复现问题，`documenter` 可以在设计阶段写文档，
`reviewer` 可以只审查其中一份高风险产物。是否调用某个角色由任务风险和所需证据决定。

## 个人助手如何按需组合

不要为了“像团队”而每次召集全部角色。先选最小足够组合：

| 任务 | 建议组合 |
| --- | --- |
| 查一个值、路径或实际命令输出 | `scout` |
| 边界清楚的小改动 | `builder`，上层助手自行检查交付 |
| 需求模糊或跨模块 | `planner -> builder`，根据风险加 `reviewer` 或 `verifier` |
| 缺陷难复现 | `verifier -> builder -> verifier` |
| 高风险方案或实现 | `planner -> reviewer -> builder -> reviewer -> verifier` |
| 数据对比或效果报告 | `worker`，结论重要时加 `reviewer` |
| 需要变更记录、commit 和交付说明 | 在前序工作后加 `documenter` |

上层助手可以在一次用户任务中动态升级：先委派 `builder`；如果发现需求未收敛，转给 `planner`；
如果实现涉及安全、数据或并发，加 `reviewer`；如果完成标准依赖现实运行，加 `verifier`。

## 角色之间交付什么

稳定的团队不靠角色名称运转，而靠交接物。上层助手把前一个角色的产物压缩成下一个角色的任务契约，不必复制整段对话历史。

### planner -> builder

- 目标、非目标、输入输出边界和必须保持的行为。
- 已批准方案与关键取舍，不再需要 builder 重做的决策。
- 影响文件/符号、契约使用点和迁移顺序。
- 编号、可判真假的验收标准与单元测试建议。
- 已知风险、假设和仍待用户确认的问题。

### builder -> reviewer / verifier

- 稳定的 diff、commit 或工作树边界。
- 验收编号到代码改动和单元测试的映射。
- 实际运行的命令和结果，包括已知既有失败。
- 最可能出错的边界、未验证环境和仍成立的假设。

### reviewer -> 产出角色

- 一句总体可接受性结论。
- 按严重度排序的编号发现。
- 每条发现的位置、触发场景、错误结果、影响、证据和修复方向。
- 未覆盖部分和存疑结论所依赖的前提。

### verifier -> documenter / builder

- 待验版本、环境、数据和与计划的偏差。
- 每条验收标准的通过/失败/阻塞/不适用判定与证据。
- 失败项的最小复现、预期与实际、关键日志。
- 证据、测试数据和未清理运行产物的路径。

### 全部角色 -> documenter

- 已批准的需求与方案、实现范围、评审结论和验证证据。
- 需要更新的文档/变更记录、目标读者和仓库惯例。
- 是否包含 commit、提交范围、提交信息约定和不包含的既有改动。
- 已知失败、阻塞、未验证项和剩余风险，不要在交付摘要中丢失。

## 编写高质量模板

### 先定义责任，再选 harness

先写清角色做哪类判断、产出什么、把什么交给谁，再选择 Claude、Codex、Pi 或 TUI harness。
同一角色可以随账号、成本或任务更换 CLI，而不改变它在团队中的语义。

### 把 description 当成路由接口

`description` 是上层助手在 `template list --json` 中能读到的选人依据。它至少说清：

1. 角色一句话职责和相对成本。
2. 什么场景选它，什么场景应考虑其他角色。
3. 调用方应提供哪些输入。
4. 它交付什么，是否可能写入工作区。
5. 并行时是否需要独立 worktree、数据集或外部环境。

不要把“精通某技术”当成职责，也不要只写一串人设形容词；那些内容无法帮助上层助手选人。

### 把 system_prompt 当成常驻工作契约

`system_prompt` 只放每个任务都成立的内容：

- 职责重心和与相邻角色的交接关系。
- 先看什么、如何建立证据、如何处理信息不足。
- 本角色特有的质量准则。
- 稳定的交付结构。
- 真实必要的安全底线。

具体 issue、文件路径、用户决定、这次要跑的命令和这次的完成标准属于 `prompt`，不属于 `system_prompt`。

角色定位是编排默认值，不是能力封禁。例如：

- `planner` 默认不承担产品实现，但它应能落盘需求、设计、实施和验收文档，也可编写可行性原型。
- `reviewer` 在独立评审结论固定前不应顺手修改被评对象，但它应能落盘评审报告；任务还委派修复时可分阶段执行。
- `verifier` 不应为了让验收通过而暗中改变被验对象，但它应能编写验证脚本、夹具、环境配置和报告。

把“不要伪造证据”、“保护与任务无关的已有改动”、“破坏性/外部操作按任务授权执行”作为安全约束；
不要为了强化角色印象，随意禁止它写自己的交付物、运行合理命令或完成 prompt 明确委派的工作。

### 用 model + effort 表达成本层级

根据错误成本、推理复杂度和调用频率分配档位：

- 方案一旦出错会让后续全部返工，`planner` 适合高档位。
- 实现和独立评审需要足够的代码理解能力，`builder`/`reviewer` 适合中高档位。
- 运行验证有大量确定性执行，`verifier` 可用中低档位；性能根因分析时临时升档。
- 单点查询高频且输出短，`scout` 适合低档位。

成本标签是相对值。不同提供方的“中成本”不能直接比较，先在实际账号和任务上校准。

### 避免职责重叠

如果两个角色对同一输入使用同一判断标准、产出同一交付物，就应考虑合并。
区分角色时优先问：它是做决策、产出、独立判断、实证，还是交付收口？

`builder-hard` 一类模板不是新职责，而是 `builder` 的高强度档位。只在高强度档位需要不同的常驻工作方式时单独建模板；
否则优先用 `run --model --effort` 临时升档，避免模板列表膨胀。

## 从开发团队改造为其他团队

不要直接复制“程序员”人设，而要复用七类工作函数：

| 开发角色 | 抽象工作函数 | 可改造的角色示例 |
| --- | --- | --- |
| `planner` | 收敛问题、定义方法和验收 | 研究组长、活动策划、调查设计师 |
| `builder` | 生产主产物 | 研究员、内容作者、数据工程师 |
| `reviewer` | 按独立标准挑错 | 同行评审、编辑、合规复核 |
| `verifier` | 用实验或现实运行证明 | 实验员、发布测试员、现场核查员 |
| `documenter` | 维护权威记录并收口交付 | 知识管理员、出版编辑、档案管理员 |
| `worker` | 承接通用分析和中间产物 | 调研助理、数据分析员、运营专员 |
| `scout` | 低成本补充单一事实 | 资料检索员、目录员、信息核对员 |

改造时逐一重写：选用场景、所需输入、交付物、证据标准、与相邻角色的交接关系和成本档位。
例如内容团队的 `verifier` 可能不跑测试命令，而是检查链接、渲染、数据引用和发布预览；研究团队的 `documenter` 可能维护方法、证据表和研究日志。

## 安装样例并校准

可复制样例位于 [`assets/development-team.yaml`](../assets/development-team.yaml)。它是可运行的起点，不是针对每台机器的最终配置。

1. 先备份现有 `~/.config/agentmux/config.yaml`，再将样例中需要的模板合并进去。
2. 将 `command`、`model` 和 `effort` 改成本机可用的 CLI、模型与成本档位。
3. 运行 `agentmux doctor --json`，解决配置、CLI 路径和档位夹取问题。
4. 运行 `agentmux template list --json`，从上层助手视角阅读所有 `description`，检查选角路由是否清晰。
5. 用一组真实任务校准：一个小实现、一个模糊方案、一个实际运行验收、一个数据分析和一个最终交付。
6. 记录误选、缺失输入、交接丢失和无效硬限制，再修改 `description` 或 `system_prompt`。

只有当不同强度档位需要不同的常驻工作方式时才新增模板。只是某次任务更难时，优先通过 `run --model --effort` 临时升档。
